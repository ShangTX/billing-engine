# 计费单元统一求值机制设计

## 日期

2026-04-20

## 一、背景

当前项目中的“条件免费”探索，本质上暴露的不是单个优惠规则问题，而是一个更高层的建模缺口：

1. Core 已经可以一次性计算出未来一段时间内的计费单元集合。
2. 但对于 `queryTime` 落在某个已生成单元内部的场景，现有模型无法统一、精确地回答“截至这个时刻，该单元应收多少”。
3. 一些规则在生成 `BillingUnit` 时过早定值，丢失了单元内部费用变化所需的信息。

以 `DayNightRule` 为例：

- `UNIT_BASED` 路径中，跨日夜边界的混合单元会先统计 `dayMinutes/nightMinutes`，再根据 `blockWeight` 一次性将整个单元定价为白天价或夜间价。
- `CONTINUOUS` 路径中，同样会在单元生成时将混合区间压缩为单一价格。

这样做的问题是：

- 单元内部任意位置的查询值不准确。
- 查询层如果想纠正，只能重新解释规则私有数据，破坏边界。
- “条件免费”被误建模成特殊逻辑，而不是统一的“单元内费用不稳定求值”问题。

因此需要引入一套统一机制，使 Core 生成的每个 `BillingUnit` 都能在不重跑规则的前提下，结合外部输入（第一阶段仅限 `queryTime`）得出该单元截至查询时刻的即时应收值。

## 二、设计目标

### 2.1 核心目标

建立一套“计费单元统一求值机制”，满足：

1. Core 一次计算出未来一段时间内的 `BillingUnit` 集合。
2. 对 `calculationEndTime` 范围内任意 `queryTime`，都可以精确查询对应费用。
3. 查询不重跑 `BillingService`，不重放规则，不重新聚合优惠。
4. 所有查询都基于已生成的 `BillingUnit` 集合和单元中保存的求值描述完成。
5. 统一覆盖以下场景：
   - 条件免费失效
   - 跨时段边界导致单元内费用逐步变化
   - 未来可能出现的按比例收费、分钟级收费等时间轴相关求值需求

### 2.2 设计原则

本设计必须遵守现有项目的基础原则：

1. **Core 只负责计算**
   查询求值机制仍属于计费域计算的一部分，不应退化成外层的规则重放逻辑。

2. **规则保持纯函数**
   规则在生成 `BillingUnit` 时输出确定的结果和确定的求值描述；查询时给定 `BillingUnit + queryTime`，结果应是确定的。

3. **同样输入得到同样输出**
   单元查询值必须是确定性计算结果，而不是依赖隐藏状态。

4. **规则实现与公共求值协议分离**
   规则负责生成求值描述；公共层负责解释求值描述并计算即时值。

5. **查询不重放规则**
   查询层只能基于单元和公共求值器工作，不能重新执行各规则内部计算流程。

## 三、问题定义

### 3.1 查询范围问题

需要明确区分两类场景：

#### 场景 A：`queryTime` 落在已生成单元内部

例如：

- 本次计算已经覆盖 `00:00-24:00`
- 某个已生成单元是 `10:00-11:00`
- 查询时间为 `10:23`

这种场景属于**单元内部即时求值**问题，是本设计解决的核心。

#### 场景 B：`queryTime` 超出当前计算范围

例如：

- 本次结果只计算到 `12:00`
- 查询时间为 `15:00`

这种场景不是“单元求值”问题，而是**结果覆盖不足**问题。

本设计明确规定：

- 如果 `queryTime > calculationEndTime`，直接报错或返回覆盖不足，不进入单元求值逻辑。

### 3.2 当前建模缺口

当前模型存在三个关键缺口：

1. `BillingUnit.chargedAmount` 的语义混杂，既像最终金额，又被查询层隐式当成当前值参考。
2. `BillingUnit.accumulatedAmount` 表示完整单元结束后的累计金额，但查询层又希望直接用它回答任意时点的金额。
3. 各规则会在单元生成阶段将“本应留待查询时解释的变化过程”提前压缩成常数。

## 四、语义定义

### 4.1 查询边界

查询必须满足：

```text
queryTime <= calculationEndTime
```

若不满足，则当前 `BillingResult` 不覆盖该查询时间，查询失败。

### 4.2 查询对象

查询只基于 Core 已经生成好的 `BillingUnit` 集合进行。

禁止：

- 重新执行 `BillingService`
- 重新执行规则
- 重新聚合优惠
- 重新生成分段或单元

### 4.3 单元求值语义

当 `queryTime` 落在某个已生成单元 `u` 内部时：

```text
u.beginTime < queryTime <= u.endTime
```

查询接口返回的是：

> 该单元截至 `queryTime` 的即时应收值

而不是：

- 该单元完整结束后的最终金额
- 查询时的预测总金额
- 某种默认展示金额

### 4.4 查询总金额语义

查询总金额定义为：

```text
所有已完成单元的完整金额
+ 当前命中单元截至 queryTime 的即时应收值
```

后续尚未到达的单元不参与金额。

### 4.5 上限语义

每个单元都存在一个上限值：

> 该单元完整结算后的理论最终金额

该值是该单元求值结果在时间轴上收敛的终点。

### 4.6 `valueSpec` 协议不变量

为了保证不同规则生成的 `valueSpec` 可被统一解释，第一阶段必须满足以下不变量：

1. 对任意可查询时间点 `t`，`valueAt(unit, t)` 必须有唯一确定值。
2. 当 `t = unit.endTime` 时，必须满足：
   ```text
   valueAt(unit, t) = unit.chargedAmount
   ```
3. `unit.chargedAmount` 是该单元完整结束后的最终金额，也是查询值的最终收敛点。
4. 第一阶段默认要求 `valueAt(unit, t)` 在时间轴上单调不减。
   - 这与当前已讨论场景一致：随着查询时间推进，费用只会维持不变或增加
   - 如果未来引入真实“先升后降”的场景，再扩展协议，不在第一阶段处理
5. 第一阶段默认要求：
   ```text
   0 <= valueAt(unit, t) <= unit.chargedAmount
   ```
   这条约束成立的前提是封顶、条件免费、比例收费等逻辑都已体现在最终 `chargedAmount` 与 `valueSpec` 中。

## 五、总体架构

设计采用两层结构：

### 5.1 公共层：统一求值协议

公共层负责定义：

1. 单元如何描述自身的时间轴求值方式
2. 给定单元和 `queryTime` 时，如何计算即时应收值
3. 查询金额如何基于单元级结果聚合

公共层不关心：

- 该单元来自哪个规则
- 为什么该单元是不稳定的
- 是条件免费、日夜比例，还是未来其他特性

### 5.2 规则层：生成求值描述

各规则负责：

1. 按现有业务规则生成 `BillingUnit`
2. 计算该单元完整结束后的最终金额
3. 如果单元内部费用随时间位置变化，则为该单元生成对应的求值描述

规则层不负责：

- 查询时如何解释 `queryTime`
- 查询金额如何聚合
- 查询视图如何裁剪

### 5.3 查询层：薄编排

查询层的职责收缩为：

1. 校验 `queryTime <= calculationEndTime`
2. 定位命中单元
3. 调用公共求值器得到该单元即时值
4. 按统一公式计算查询总金额

查询层不再直接解释规则私有结构。

### 5.4 长期简化与精确查询边界

长期计费简化单元（simplified unit）与“任意分钟精确查询”属于天然冲突的使用场景：

- simplification 的目标是压缩长时间范围内的详细过程
- 精确查询的目标是保留单元内部时间轴信息并精确求值

因此本设计明确规定：

1. simplified unit 不参与单元内即时求值。
2. 如果查询命中 simplified unit，说明当前结果不适合直接做精确查询。
3. 此时由 `billing-api` 层触发一次“精确重算”分支，返回一个不含 simplification 的精确结果，再继续查询。

也就是说：

- Core 仍可在长周期场景下产出简化结果
- 但精确查询是一个更高优先级能力
- 当两者冲突时，以精确查询为准，由 API 层主动降级为精确结果

## 六、核心模型

### 6.1 BillingUnit 语义重定义

`BillingUnit` 仍然是最小计费单位，但语义需要扩展为：

1. 一个确定的时间范围
2. 一个完整结束后的最终金额载体
3. 一个可按 `queryTime` 求即时值的对象

### 6.2 `chargedAmount` 语义

`chargedAmount` 直接重定义为：

> 该单元完整结束后的最终金额

不保留旧的模糊语义，也不新增并行的 `finalAmount` 字段。

### 6.3 `accumulatedAmount` 语义

`accumulatedAmount` 保留，定义为：

> 该单元完整结束后的累计金额

它不能直接回答任意 `queryTime` 下的查询金额，只作为查询时的前缀累计锚点。

### 6.4 新增公共字段：`valueSpec`

每个 `BillingUnit` 都新增一个统一字段，以下以 `valueSpec` 作为占位名称描述：

> 单元内时间轴求值描述

设计要求：

1. 所有单元统一携带 `valueSpec`
2. 稳定单元的 `valueSpec` 退化为固定值描述
3. 不稳定单元的 `valueSpec` 描述其在时间轴上的取值变化

### 6.5 `ruleData`

`ruleData` 继续保留，但降级为规则私有解释数据：

- 调试
- 规则内部留痕
- 辅助展示

禁止继续将公共查询求值协议塞入 `ruleData`。

## 七、统一查询公式

对于命中单元 `u`，查询时间 `t` 满足：

```text
u.beginTime < t <= u.endTime
```

查询金额计算公式为：

```text
queryAmount = u.accumulatedAmount - u.chargedAmount + valueAt(u, t)
```

其中：

- `u.accumulatedAmount`：该单元完整结束后的累计金额
- `u.chargedAmount`：该单元完整结束后的最终金额
- `valueAt(u, t)`：该单元截至 `t` 的即时应收值

### 7.1 公式含义

该公式本质上等价于：

```text
前一个已完成单元的累计金额 + 当前命中单元即时应收值
```

但不需要额外扫描前一个单元，因此适合直接实现。

### 7.2 收敛特性

当 `t = u.endTime` 时，应满足：

```text
valueAt(u, t) = u.chargedAmount
```

因此公式自然退化为：

```text
queryAmount = u.accumulatedAmount
```

这保证了查询值在单元结束时与完整结果一致。

### 7.3 simplified unit 的查询策略

对于 simplified unit，不直接适用上述公式。

原因是：

- simplified unit 本身不包含足够的单元内时间轴信息
- 其存在目的就是压缩详细过程

因此：

1. 若查询命中普通单元，使用统一公式直接求值
2. 若查询命中 simplified unit，由 `billing-api` 触发精确重算后再查询

## 八、`valueSpec` 的协议与表达模型

### 8.1 协议层与表达层分离

`valueSpec` 的设计分成两层：

1. **协议层**
   统一定义“给定时间位置，如何求即时值”
2. **表达层**
   不同规则使用不同的内部表达模型来实现该协议

这意味着：

- 公共层先统一求值协议
- 不强制所有规则都使用同一种内部表达方式

### 8.2 第一阶段支持范围

第一阶段公共求值协议只支持**时间轴相关外部参数**，即：

- `queryTime`

暂不支持任意业务上下文参数。

这样可以先把当前最核心的问题做纯做稳。

### 8.3 第一阶段推荐表达模型

第一阶段建议优先实现以下几类表达：

1. **固定值描述**
   - 单元内部任意位置取值恒定
   - 用于稳定单元

2. **阶跃值描述**
   - 在某个临界时刻发生值跳变
   - 用于条件免费等场景

3. **分段累计描述**
   - 随 `queryTime` 推进，在多个区间内按不同规则累计
   - 用于 `DayNightRule` 等跨边界混合单元

### 8.4 分钟级扩展要求

虽然第一阶段不一定实现分钟级描述，但协议层必须允许未来扩展出更细粒度表达，例如：

- 每分钟采样值
- 每分钟累计值
- 更高精度的离散时间点列表

这意味着设计时不能将 `valueSpec` 限死为“只能由少数几段构成”，而应将“分段函数/分段修正”视为第一阶段实现，而不是唯一形式。

### 8.5 封顶进入 `valueSpec`

封顶逻辑不能留在单元外层临时裁剪，而必须进入 `valueSpec` 的建模范围。

原因是：

1. 查询时需要保证 `valueAt(unit, queryTime)` 与单元最终 `chargedAmount` 一致收敛
2. 若封顶只体现在 `chargedAmount/accumulatedAmount`，但不进入 `valueSpec`，则命中封顶单元内部查询时没有唯一语义

因此本设计明确规定：

- 单元的 `valueSpec` 必须直接表达“已考虑封顶后的即时值”
- `valueAt(unit, queryTime)` 返回的是已包含封顶效果的即时应收值
- 查询层不再对命中单元额外套一层封顶裁剪

## 九、`DayNightRule` 映射方案

### 9.1 当前问题

当前 `DayNightRule` 的主要缺陷是：

1. 在生成混合单元时，已经计算了 `dayMinutes/nightMinutes`
2. 但最终仍根据 `blockWeight` 一次性将整个单元定价为白天价或夜间价
3. 单元内部动态变化过程被压缩为常数

因此：

- 规则层内部知道变化过程
- 但输出的 `BillingUnit` 不再保留足够信息
- 查询无法精确回答单元内部任意时刻的应收值

### 9.2 新模型下的职责

`DayNightRule` 仍负责：

1. 生成单元边界
2. 计算该单元完整结束后的最终金额
3. 生成该单元的 `valueSpec`

但不再在混合单元上过早压缩信息。

### 9.3 `UNIT_BASED` 路径

对于 `UNIT_BASED`：

- 当前 `UnitWithContext` 已经保存了 `dayMinutes/nightMinutes`
- 新设计下，应进一步保留足够的单元内时间分段信息
- 最终生成：
  - `chargedAmount`：完整结束后的最终金额
  - `valueSpec`：描述该单元内部随着时间推进如何累计到最终金额

### 9.4 `CONTINUOUS` 路径

对于 `CONTINUOUS`：

- 当前 `splitTimeAxis()` 只按免费时段边界切分，不记录日夜内部变化
- 新设计下，规则层需要在生成收费单元时补全单元内部时间构成信息
- `TimeFragment` 不必强制保持现状，可以扩展或改造为更适合生成 `valueSpec` 的中间表示

### 9.5 收敛性结论

`DayNightRule` 的“日夜分钟占比如何影响单元价格”属于规则私有逻辑；  
但“该单元在时间轴上如何从当前值收敛到最终值”属于公共求值协议范畴。

因此：

- 规则私有：生成边界、比例、分段累计信息
- 公共层统一：解释 `valueSpec`，计算 `valueAt(unit, queryTime)`

这证明该问题可以收敛到公共层。

## 十、“条件免费”的重新定位

### 10.1 不再作为独立核心机制

“条件免费”不再作为单独的查询机制存在。

它在新模型中只是：

> 一类特殊的时间轴求值描述

### 10.2 映射方式

例如“超过某时刻后免费失效”可以表示为：

- 某时刻前：即时值为减免后的值
- 某时刻后：即时值恢复为正常值

这就是一个阶跃型 `valueSpec`，而不是单独的 `conditionalFree` 字段体系。

### 10.3 字段处理

以下字段应从核心语义中移除：

- `conditionalFree`
- `conditionalFreeUntil`

它们不再作为主路径查询逻辑依赖字段。

### 10.4 优惠等效金额的边界

优惠等效金额分析不进入即时查询主路径。

本设计明确规定：

1. 即时查询只负责返回指定 `queryTime` 下的精确应收值
2. 优惠等效金额仍基于“完整计算完成后的最终结果”进行分析
3. 只要完整结果中的 `chargedAmount`、`accumulatedAmount`、`valueSpec` 最终一致，优惠等效金额逻辑就不受即时查询机制影响

## 十一、对现有代码结构的影响

### 11.1 BillingResultViewer

`BillingResultViewer` 需要改造成薄编排器：

1. 校验查询时间范围
2. 定位命中单元
3. 如果命中 simplified unit，则触发精确重算分支
4. 调用公共求值器
5. 按统一公式计算查询金额

它不再解释：

- `ruleData.uncertainty`
- 条件免费特例
- 规则私有片段结构

### 11.1.1 `effectiveTo` 语义修正

当前 `effectiveTo` 不能继续简单等于命中单元的 `endTime`。

在新模型下，`effectiveTo` 应重定义为：

> 从当前查询结果出发，下一次查询值可能发生变化的最早边界点

这个边界点由命中单元的 `valueSpec` 决定，而不是由单元结束时间直接决定。

因此：

- 对稳定单元，`effectiveTo` 可以等于单元 `endTime`
- 对不稳定单元，`effectiveTo` 应等于 `valueSpec` 中的下一变化点

### 11.2 规则实现

各规则需要从“直接输出最终定值单元”迁移到：

- 输出最终定值
- 输出公共求值描述

尤其是：

- `DayNightRule`
- `RelativeTimeRule`
- `CompositeTimeRule`

这些存在单元内部变化可能的规则都需要检查并补全 `valueSpec` 生成逻辑。

### 11.3 测试结构

当前 `ConditionalFreePromotionTest`、`StartFreePromotionTest` 主要是打印式场景验证，不能作为最终设计的可靠回归保证。

后续应补充：

1. 公共求值器的单元测试
2. `DayNightRule` 混合单元的断言测试
3. 查询金额公式的断言测试
4. `queryTime > calculationEndTime` 的边界测试
5. 命中 simplified unit 时触发精确重算的测试
6. `effectiveTo` 取下一变化点的测试
7. 封顶命中单元内部查询的断言测试

## 十二、阶段性实施建议

### 12.1 第一阶段

先完成公共框架搭建：

1. 统一 `chargedAmount` / `accumulatedAmount` 语义
2. 新增 `valueSpec`
3. 建立公共求值器
4. 改造 `BillingResultViewer`
5. 明确 simplified unit 的精确查询降级分支

### 12.2 第二阶段

先接入最能验证模型价值的规则：

1. `DayNightRule`
2. 条件免费对应的 `StartFreePromotionRule`
3. 封顶命中单元的 `valueSpec` 表达

### 12.3 第三阶段

再推广到：

1. `RelativeTimeRule`
2. `CompositeTimeRule`
3. 未来分钟级求值场景

## 十三、结论

本设计将当前零散的“条件免费”“查询恢复原价”“混合单元近似定价”等问题，统一提升为：

> 已生成计费单元在时间轴上的即时求值问题

通过引入统一的 `valueSpec` 和公共求值器，可以实现：

1. 查询不重跑规则
2. 查询仅依赖已生成单元
3. 对 `calculationEndTime` 范围内任意时间点精确求值
4. 将规则私有逻辑与公共求值协议清晰分离

这比继续扩展“条件免费”特例更符合当前项目的长期设计方向。
