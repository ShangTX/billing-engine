# Billing Engine TODO Roadmap

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this roadmap item-by-item. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 按当前 `billing-engine` 的能力现状和 TODO 优先级，制定一条从设计收敛到能力扩展的渐进完成路线，避免在复杂规则和调用侧压力下偏离核心引擎设计原则。

**Architecture:** 先处理“会影响后续所有能力实现”的基础问题，再处理规则语义统一，再扩展新规则和新优惠，最后完善测试工具和文档。路线图不直接替代各子事项的详细实施计划；每个阶段落地前，应再生成独立 plan。

**Tech Stack:** Java 21, Maven Toolchains, `core`, `billing-api`, `bill-test`, JUnit 5

---

## 当前状态快照

- `relativeTime` 当前在停车验收语义下已基本对齐，不是当前主风险点。
- `dayNight` 当前剩余差异已显著收敛，且已确认至少一部分历史差异属于旧调用方的截断颗粒历史行为，而不是核心引擎必须兼容的目标。
- `billing-engine` 当前更值得优先处理的问题，不是新增能力数量，而是核心边界和规则复杂度已经开始膨胀。

## 路线图原则

- 先处理会影响多个 TODO 的公共基础，再处理单点能力。
- 先统一语义和边界，再扩展新规则和优惠。
- 不把调用方历史行为直接回灌为通用引擎设计。
- `core` 优先保持纯计算；`billing-api` 只消费公共契约；`bill-test` 不反向决定核心设计。

## 推荐完成顺序

### Phase 0: 先收敛核心边界

对应事项：

- `TODO-20260514-007` 收敛核心引擎职责边界与规则复杂度

原因：

- 这是当前所有后续能力实现的前置条件。
- 如果不先处理边界问题，后续每做一个功能，`DayNightRule` / `RelativeTimeRule` / `CompositeTimeRule` 只会继续膨胀。
- `billing-api` 对 `ruleData` 的直接理解，以及 simplification 协议通过 `Map<String, Object>` 传播，已经属于结构性风险。

阶段目标：

- 明确 `core` 公共契约、规则私有语义、`billing-api` 查询层、`bill-test` 工具层的边界。
- 形成规则大类拆分方向。
- 给 simplification / 精确查询回退设计出更稳定的公共协议。

- [ ] 先完成 `TODO-20260514-007` 的设计收敛，再开始后续能力扩展。

### Phase 1: 统一单元语义

对应事项：

- `TODO-20260508-005` 统一跨时间段计费单元处理方式
- `TODO-20260508-004` 支持不完整计费单元的多种计费方式

原因：

- 这两个事项共同决定 `BillingUnit` 的边界语义，是后续所有规则扩展的基础。
- `dayNight`、`relativeTime`、`compositeTime` 当前对跨段单元和不完整单元的处理并不统一。
- 如果先做新规则或新优惠，再回头改单元语义，回归面会显著扩大。

阶段目标：

- 统一跨时间段单元的处理策略（截断、跨越等）。
- 明确不完整单元的计费模式和默认行为。
- 明确 `chargedAmount`、`accumulatedAmount`、`valueSpec` 在这两类场景下的契约。

- [ ] 先做 `TODO-20260508-005` 的语义设计与基线测试。
- [ ] 再做 `TODO-20260508-004`，把不完整单元模式建立在统一单元语义之上。

### Phase 2: 扩展自然时间规则能力

对应事项：

- `TODO-20260508-006` 新增多自然时段计费规则

原因：

- 多自然时段规则本质上依赖 Phase 1 的跨时段与不完整单元语义。
- 如果在 Phase 1 之前实现，会把尚未稳定的边界复制到新规则里。

阶段目标：

- 明确它与 `dayNight`、`compositeTime` 的边界。
- 决定是新增规则，还是抽象现有规则能力后组合实现。
- 保证查询时点金额和完整结算金额契约一致。

- [ ] 只有在 Phase 1 完成后，才启动 `TODO-20260508-006`。

### Phase 3: 补齐优惠能力

对应事项：

- `TODO-20260508-001` 实现金额减免和折扣优惠

原因：

- 金额减免和折扣优惠要建立在稳定的单元语义和结算顺序上。
- 如果先做优惠，再回头修改单元语义，很容易导致优惠等效金额、查询时点金额和结转语义全部重算。

阶段目标：

- 明确 `AMOUNT`、`DISCOUNT` 与 `FREE_RANGE`、`FREE_MINUTES` 的组合顺序。
- 明确它们对 `PromotionEquivalentCalculator` 和 `BillingResultViewer` 的影响范围。
- 保持优惠能力仍通过公共模型表达，而不是侵入具体规则内部。

- [ ] 在 Phase 1 稳定后，再启动 `TODO-20260508-001`。

### Phase 4: 决策预留规则常量

对应事项：

- `TODO-20260508-002` 落地预留计费规则常量

原因：

- 这是一个“产品/架构决策项”，不是实现优先项。
- 在核心边界、单元语义和新自然时段规则都更清晰之后，再决定 `times`、`naturalTime`、`nrTimeMix` 是实现、合并还是废弃，成本最低。

阶段目标：

- 给每个预留常量一个明确状态。
- 清理 README / USER_GUIDE 中的模糊描述。

- [ ] 在 Phase 2 之后处理 `TODO-20260508-002`。

### Phase 5: 扩展测试结果生成器

对应事项：

- `TODO-20260508-003` 扩展测试结果生成器规则覆盖

原因：

- 生成器属于测试工具层，应该建立在核心能力已经稳定之后扩展。
- 如果过早扩展，容易让工具代码反向固化尚未稳定的规则设计。

阶段目标：

- 把已经稳定的规则能力补到生成器里。
- 明确生成器只生成“结果样本”，不承担设计判断职责。

- [ ] 作为最后一个阶段处理 `TODO-20260508-003`。
